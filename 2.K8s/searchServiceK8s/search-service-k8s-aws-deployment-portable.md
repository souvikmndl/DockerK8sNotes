# Deploying a Go Search Service + Postgres to Kubernetes on AWS (EKS)

An end-to-end, copy-pasteable runbook: write a small Go **document search service** backed by
**PostgreSQL full-text search**, containerize both, run the whole stack locally, then ship it to a
real **Amazon EKS** cluster fronted by an **ALB**.

> **Design choice up front:** the service uses **Postgres full-text search** (`tsvector` + GIN index)
> rather than Elasticsearch. For a "simple search service" this keeps the moving parts to two
> containers while still being a *real* ranked search. If you later outgrow Postgres FTS (fuzzy
> matching, huge corpora, relevance tuning), the swap target is OpenSearch/Elasticsearch — but don't
> pay that operational cost until you need it.

## 2. The Go search service

### 2.1 `go.mod`

```go
module github.com/souvik/search-service

go 1.22

require github.com/jackc/pgx/v5 v5.6.0
```

`pgx` is the de-facto Postgres driver/toolkit for Go — faster than `lib/pq`, actively maintained, and
`pgxpool` gives you a production-grade connection pool for free. Run `go mod tidy` to fetch it and
generate `go.sum`.

### 2.2 `main.go`

Single-file service on purpose — stdlib router (Go 1.22 method-based routing), a pooled DB, graceful
shutdown, and `/healthz` + `/readyz` split (liveness vs readiness — Kubernetes treats them differently).

```go
package main

import (
	"context"
	"encoding/json"
	"errors"
	"fmt"
	"log"
	"net/http"
	"os"
	"os/signal"
	"syscall"
	"time"

	"github.com/jackc/pgx/v5/pgxpool"
)

type Document struct {
	ID    int64   `json:"id"`
	Title string  `json:"title"`
	Body  string  `json:"body"`
	Rank  float64 `json:"rank,omitempty"`
}

type server struct{ db *pgxpool.Pool }

func env(k, def string) string {
	if v := os.Getenv(k); v != "" {
		return v
	}
	return def
}

func dsn() string {
	// Prefer a full DATABASE_URL (local/compose); otherwise assemble from PG* vars (k8s pattern:
	// password comes from a Secret via secretKeyRef, everything else from a ConfigMap).
	if u := os.Getenv("DATABASE_URL"); u != "" {
		return u
	}
	return fmt.Sprintf("postgres://%s:%s@%s:%s/%s?sslmode=%s",
		env("PGUSER", "search"), os.Getenv("PGPASSWORD"),
		env("PGHOST", "localhost"), env("PGPORT", "5432"),
		env("PGDATABASE", "searchdb"), env("PGSSLMODE", "disable"))
}

func main() {
	ctx := context.Background()
	pool, err := pgxpool.New(ctx, dsn())
	if err != nil {
		log.Fatalf("connect db: %v", err)
	}
	defer pool.Close()

	s := &server{db: pool}
	mux := http.NewServeMux()
	mux.HandleFunc("GET /healthz", s.healthz)   // liveness: is the process up?
	mux.HandleFunc("GET /readyz", s.readyz)     // readiness: can it serve (DB reachable)?
	mux.HandleFunc("POST /documents", s.addDocument)
	mux.HandleFunc("GET /search", s.search)

	srv := &http.Server{
		Addr:         ":" + env("PORT", "8080"),
		Handler:      mux,
		ReadTimeout:  5 * time.Second,
		WriteTimeout: 10 * time.Second,
	}

	go func() {
		log.Printf("listening on %s", srv.Addr)
		if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
			log.Fatalf("server: %v", err)
		}
	}()

	// Graceful shutdown — lets in-flight requests finish when k8s sends SIGTERM during a rollout.
	stop := make(chan os.Signal, 1)
	signal.Notify(stop, syscall.SIGINT, syscall.SIGTERM)
	<-stop
	log.Println("shutting down…")
	shCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	_ = srv.Shutdown(shCtx)
}

func (s *server) healthz(w http.ResponseWriter, _ *http.Request) {
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte("ok"))
}

func (s *server) readyz(w http.ResponseWriter, r *http.Request) {
	ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
	defer cancel()
	if err := s.db.Ping(ctx); err != nil {
		http.Error(w, "db not ready", http.StatusServiceUnavailable)
		return
	}
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte("ready"))
}

func (s *server) addDocument(w http.ResponseWriter, r *http.Request) {
	var d Document
	if err := json.NewDecoder(r.Body).Decode(&d); err != nil {
		http.Error(w, "invalid json", http.StatusBadRequest)
		return
	}
	if d.Title == "" || d.Body == "" {
		http.Error(w, "title and body required", http.StatusBadRequest)
		return
	}
	// search_vector is a GENERATED column — we never write it, Postgres maintains it.
	err := s.db.QueryRow(r.Context(),
		`INSERT INTO documents (title, body) VALUES ($1, $2) RETURNING id`,
		d.Title, d.Body).Scan(&d.ID)
	if err != nil {
		http.Error(w, "insert failed", http.StatusInternalServerError)
		return
	}
	writeJSON(w, http.StatusCreated, d)
}

func (s *server) search(w http.ResponseWriter, r *http.Request) {
	q := r.URL.Query().Get("q")
	if q == "" {
		http.Error(w, "q is required", http.StatusBadRequest)
		return
	}
	// websearch_to_tsquery understands "quoted phrases" and OR/-, like a real search box.
	// ts_rank scores by match quality; the GIN index makes the @@ match fast.
	rows, err := s.db.Query(r.Context(),
		`SELECT id, title, body,
		        ts_rank(search_vector, websearch_to_tsquery('english', $1)) AS rank
		   FROM documents
		  WHERE search_vector @@ websearch_to_tsquery('english', $1)
		  ORDER BY rank DESC
		  LIMIT 20`, q)
	if err != nil {
		http.Error(w, "query failed", http.StatusInternalServerError)
		return
	}
	defer rows.Close()

	results := []Document{}
	for rows.Next() {
		var d Document
		if err := rows.Scan(&d.ID, &d.Title, &d.Body, &d.Rank); err != nil {
			http.Error(w, "scan failed", http.StatusInternalServerError)
			return
		}
		results = append(results, d)
	}
	writeJSON(w, http.StatusOK, map[string]any{"query": q, "results": results})
}

func writeJSON(w http.ResponseWriter, code int, v any) {
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(code)
	_ = json.NewEncoder(w).Encode(v)
}
```

### 2.3 The schema — `migrations/001_init.sql`

```sql
CREATE TABLE IF NOT EXISTS documents (
    id            BIGSERIAL PRIMARY KEY,
    title         TEXT NOT NULL,
    body          TEXT NOT NULL,
    -- Generated, always-in-sync search column. Title weighted 'A' (highest), body 'B'.
    search_vector tsvector GENERATED ALWAYS AS (
        setweight(to_tsvector('english', coalesce(title, '')), 'A') ||
        setweight(to_tsvector('english', coalesce(body,  '')), 'B')
    ) STORED,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- GIN index is what makes @@ lookups fast on tsvector. Without it, search does a full table scan.
CREATE INDEX IF NOT EXISTS idx_documents_search ON documents USING GIN (search_vector);
```

**Why this design (staff-level talking points):**
- **Generated `STORED` column** → the search vector is always consistent with the data and never
  computed at query time. No trigger to maintain, no app code to keep in sync.
- **`setweight` A/B** → a query hit in the title ranks above the same hit in the body.
- **GIN index** → inverted index over lexemes; turns `@@` from O(rows) into an index lookup.
- **`websearch_to_tsquery`** → accepts human query syntax (`"exact phrase"`, `foo or bar`, `-exclude`).

## 3. Run it locally first (fail fast, cheaply)

Spin up just Postgres in Docker, point the app at it, and confirm the whole thing works before you
touch containers-of-your-own-app or the cloud.

```bash

  -e POSTGRES_USER=search -e POSTGRES_PASSWORD=searchpass -e POSTGRES_DB=searchdb \
  postgres:16

docker exec -i pg psql -U search -d searchdb < migrations/001_init.sql

# run the app against it

```

In another terminal:


## 4. Containerize the Go app

### 4.1 `Dockerfile` (multi-stage, tiny + non-root)

```dockerfile
# ---- build stage ----
FROM golang:1.22-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
# static binary: no libc dependency, so it runs in a scratch/distroless image
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /out/search-service .

# ---- runtime stage ----
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/search-service /search-service
EXPOSE 8080
USER nonroot:nonroot
ENTRYPOINT ["/search-service"]
```

**Why multi-stage + distroless:** the build stage has the whole Go toolchain (~300 MB); the final
image ships *only* the static binary on a **distroless** base — no shell, no package manager, runs as
**non-root**. Result is a ~15–20 MB image with a tiny attack surface. Smaller image = faster pulls =
faster pod startup and scaling.

### 4.2 `.dockerignore`

```
.git
*.md
k8s/
docker-compose.yml
Dockerfile
```

Keeps the build context small and stops secrets/junk from leaking into the image layers.

### 4.3 Build & smoke-test the image

```bash
docker build -t search-service:v1 .
docker images search-service:v1        # confirm it's small

# quick run against the local pg from step 3 (host networking shortcut on Linux):
docker run --rm -p 8080:8080 \
  -e DATABASE_URL='postgres://search:searchpass@host.docker.internal:5432/searchdb?sslmode=disable' \
  search-service:v1
```

## 6. Kubernetes manifests

All manifests live in `k8s/`. Order matters at apply time (namespace → config/secrets → db → migrate
→ app → ingress). We build the design one concern at a time.

### 6.1 Namespace — `k8s/namespace.yaml`

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: search
```

### 6.2 Secret + ConfigMap — credentials vs plain config

```yaml
# k8s/db-credentials.yaml   (Secret: password lives ONLY here)
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
  namespace: search
type: Opaque
stringData:
  POSTGRES_USER: search          # consumed by the postgres container's init
  POSTGRES_PASSWORD: searchpass
  POSTGRES_DB: searchdb
  PGPASSWORD: searchpass         # consumed by the app + psql (migration job)
```
```yaml
# k8s/app-config.yaml   (ConfigMap: non-secret connection details)
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: search
data:
  PGHOST: postgres               # resolves to the postgres Service (below)
  PGPORT: "5432"
  PGDATABASE: searchdb
  PGUSER: search
  PGSSLMODE: disable
  PORT: "8080"
```

> **Note:** a `Secret` is only base64-encoded, not encrypted, at the manifest level. Fine for a demo;
> section 11 covers doing this properly (Secrets Manager / Sealed Secrets) and never committing it.

### 6.3 Postgres — `k8s/postgres.yaml` (StatefulSet + headless Service + PVC)

```yaml
apiVersion: v1
kind: Service
metadata:
  name: postgres
  namespace: search
spec:
  clusterIP: None        # headless: gives the StatefulSet pod a stable DNS name
  selector:
    app: postgres
  ports:
    - port: 5432
      name: postgres
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
  namespace: search
spec:
  serviceName: postgres
  replicas: 1
  selector:
    matchLabels: { app: postgres }
  template:
    metadata:
      labels: { app: postgres }
    spec:
      containers:
        - name: postgres
          image: postgres:16
          ports: [{ containerPort: 5432 }]
          envFrom:
            - secretRef: { name: db-credentials }
          env:
            - name: PGDATA
              value: /var/lib/postgresql/data/pgdata   # subdir avoids "lost+found" init errors
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
          readinessProbe:
            exec: { command: ["pg_isready", "-U", "search", "-d", "searchdb"] }
            initialDelaySeconds: 10
            periodSeconds: 5
          resources:
            requests: { cpu: 100m, memory: 256Mi }
            limits:   { memory: 512Mi }
  volumeClaimTemplates:
    - metadata: { name: data }
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: gp3     # EKS: dynamically provisions an EBS volume (see 8.4).
        resources:                # For local kind/minikube, delete this line to use the default SC.
          requests: { storage: 5Gi }
```

**Why a StatefulSet, not a Deployment:** databases need **stable identity and stable storage**. A
StatefulSet gives the pod a predictable name (`postgres-0`), a stable DNS entry via the headless
Service, and — crucially — reattaches *the same* PVC on restart. A Deployment's pods are
interchangeable and would happily orphan your data. (Caveat: one replica is not HA — see section 11.)

### 6.4 Schema migration — `k8s/migration.yaml` (ConfigMap + Job)

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: db-migrations
  namespace: search
data:
  001_init.sql: |
    CREATE TABLE IF NOT EXISTS documents (
        id BIGSERIAL PRIMARY KEY,
        title TEXT NOT NULL,
        body TEXT NOT NULL,
        search_vector tsvector GENERATED ALWAYS AS (
            setweight(to_tsvector('english', coalesce(title,'')), 'A') ||
            setweight(to_tsvector('english', coalesce(body,'')), 'B')
        ) STORED,
        created_at TIMESTAMPTZ NOT NULL DEFAULT now()
    );
    CREATE INDEX IF NOT EXISTS idx_documents_search ON documents USING GIN (search_vector);
---
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migrate
  namespace: search
spec:
  backoffLimit: 5
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: migrate
          image: postgres:16
          command: ["sh", "-c"]
          args:
            - |
              until pg_isready -h postgres -U "$POSTGRES_USER"; do echo waiting for db; sleep 2; done
              psql -h postgres -U "$POSTGRES_USER" -d "$POSTGRES_DB" -f /migrations/001_init.sql
          envFrom:
            - secretRef: { name: db-credentials }   # provides PGPASSWORD for psql
          volumeMounts:
            - name: migrations
              mountPath: /migrations
      volumes:
        - name: migrations
          configMap: { name: db-migrations }
```

**Why a Job, not app-side auto-migrate:** schema changes should run **once**, not on every one of N app
replicas racing each other at startup. A Job runs to completion exactly once and blocks nothing else.
(`CREATE ... IF NOT EXISTS` also keeps it idempotent.)

### 6.5 The app — `k8s/app.yaml` (Deployment + Service + HPA)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: search-service
  namespace: search
spec:
  replicas: 2
  selector:
    matchLabels: { app: search-service }
  template:
    metadata:
      labels: { app: search-service }
    spec:
      containers:
        - name: search-service
          image: IMAGE_PLACEHOLDER          # local tag for kind; ECR URL for EKS (see 8.1)
          ports: [{ containerPort: 8080 }]
          envFrom:
            - configMapRef: { name: app-config }
          env:
            - name: PGPASSWORD               # password pulled from the Secret, not the ConfigMap
              valueFrom:
                secretKeyRef: { name: db-credentials, key: PGPASSWORD }
          readinessProbe:                    # gate traffic until the DB is reachable
            httpGet: { path: /readyz, port: 8080 }
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:                     # restart if the process wedges
            httpGet: { path: /healthz, port: 8080 }
            initialDelaySeconds: 10
            periodSeconds: 15
          resources:
            requests: { cpu: 50m,  memory: 64Mi }   # requests drive scheduling + HPA math
            limits:   { cpu: 250m, memory: 128Mi }
---
apiVersion: v1
kind: Service
metadata:
  name: search-service
  namespace: search
spec:
  selector: { app: search-service }
  ports:
    - port: 80
      targetPort: 8080
  type: ClusterIP
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: search-service
  namespace: search
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: search-service
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }
```

**Why these bits matter:** the **readiness probe on `/readyz`** stops the Service from routing traffic
to a pod whose DB connection isn't up yet — no 500s during rollout. **Resource `requests`** are what
the scheduler and the **HPA** reason about (70% of `50m` CPU). Without requests, the HPA has no
baseline and can't scale.

### 6.6 Ingress — `k8s/ingress.yaml` (ALB on EKS)

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: search-service
  namespace: search
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip        # send traffic straight to pod IPs
    alb.ingress.kubernetes.io/healthcheck-path: /healthz
spec:
  ingressClassName: alb
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: search-service
                port: { number: 80 }
```

This is a no-op on a local cluster (no ALB controller there) — apply it only on EKS after section 8.5.

## 8. Deploy to AWS (EKS)

Set shared env once:

```bash
export AWS_REGION=ap-south-1
export CLUSTER=search-demo
export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
export ECR=$ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com
```

### 8.1 Push the image to Amazon ECR

```bash
aws ecr create-repository --repository-name search-service --region $AWS_REGION

aws ecr get-login-password --region $AWS_REGION \
  | docker login --username AWS --password-stdin $ECR

# IMPORTANT on Apple Silicon / ARM: build for the cluster's arch (amd64 nodes)
docker build --platform linux/amd64 -t search-service:v1 .

docker tag search-service:v1 $ECR/search-service:v1
docker push $ECR/search-service:v1
```

> The `--platform linux/amd64` flag is the single most common "works locally, `exec format error` in
> the cluster" gotcha when you're on an M-series Mac.

### 8.2 Create the EKS cluster

```bash
eksctl create cluster \
  --name $CLUSTER \
  --region $AWS_REGION \
  --version 1.30 \
  --nodegroup-name workers \
  --node-type t3.medium \
  --nodes 2 --nodes-min 2 --nodes-max 4 \
  --managed \
  --with-oidc            # sets up the OIDC provider — required for IRSA (IAM Roles for Service Accounts)
```

This provisions the **AWS-managed control plane** + a **managed node group** and wires kubeconfig.
Takes ~15–20 minutes (it's building a VPC, subnets, the control plane, and EC2 nodes under the hood).

> **`--with-oidc` is not optional here.** Both the EBS CSI driver and the Load Balancer Controller need
> **IRSA** — pods assuming IAM roles via a ServiceAccount — and that requires the cluster's OIDC
> provider to be associated. (Standalone: `eksctl utils associate-iam-oidc-provider --cluster $CLUSTER --region $AWS_REGION --approve`.)

### 8.3 Point kubectl at it

```bash
aws eks update-kubeconfig --name $CLUSTER --region $AWS_REGION
kubectl get nodes            # should list 2 Ready nodes
```

### 8.4 Enable dynamic EBS storage (for the Postgres PVC)

Modern EKS does **not** ship in-tree EBS provisioning — you add the **EBS CSI driver** addon, with an
IAM role so it can create volumes:

```bash
# IAM role for the driver (IRSA)
eksctl create iamserviceaccount \
  --name ebs-csi-controller-sa --namespace kube-system \
  --cluster $CLUSTER --region $AWS_REGION \
  --attach-policy-arn arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy \
  --approve --role-only --role-name AmazonEKS_EBS_CSI_DriverRole

# install the managed addon, bound to that role
eksctl create addon --name aws-ebs-csi-driver --cluster $CLUSTER --region $AWS_REGION \
  --service-account-role-arn arn:aws:iam::$ACCOUNT_ID:role/AmazonEKS_EBS_CSI_DriverRole --force
```

Create a `gp3` StorageClass (`k8s/gp3-storageclass.yaml` — cluster-scoped, no namespace):

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer   # wait to bind until a pod is scheduled -> right AZ
parameters:
  type: gp3
```

```bash
kubectl apply -f k8s/gp3-storageclass.yaml
```

`WaitForFirstConsumer` matters: an EBS volume is AZ-locked, so you delay provisioning until the
scheduler has picked a node/AZ — otherwise you can create a volume in an AZ with no room for the pod.

### 8.5 Install the AWS Load Balancer Controller (for the Ingress → ALB)

```bash
# 1) IAM policy (using main tracks the current policy; pin a version tag for reproducible infra)
curl -o iam_policy.json \
  https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/main/docs/install/iam_policy.json
aws iam create-policy --policy-name AWSLoadBalancerControllerIAMPolicy \
  --policy-document file://iam_policy.json

# 2) IRSA ServiceAccount the controller runs as
eksctl create iamserviceaccount \
  --cluster $CLUSTER --region $AWS_REGION \
  --namespace kube-system --name aws-load-balancer-controller \
  --attach-policy-arn arn:aws:iam::$ACCOUNT_ID:policy/AWSLoadBalancerControllerIAMPolicy \
  --approve

# 3) install via Helm
helm repo add eks https://aws.github.io/eks-charts
helm repo update eks
helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName=$CLUSTER \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller

kubectl -n kube-system rollout status deploy/aws-load-balancer-controller
```

The controller watches for `Ingress` objects with `ingressClassName: alb` and provisions a real
**Application Load Balancer** to match — that's how your Ingress manifest becomes a public URL.

> **Shortcut worth knowing:** newer clusters can use **EKS Auto Mode**, which bundles load balancing
> and storage so you skip steps 8.4–8.5 entirely. This guide does it the explicit way so you
> understand what Auto Mode is doing for you.

### 8.6 Deploy the application

```bash
# point the Deployment at your ECR image
sed "s#IMAGE_PLACEHOLDER#$ECR/search-service:v1#" k8s/app.yaml > /tmp/app.eks.yaml

kubectl apply -f k8s/namespace.yaml
kubectl apply -f k8s/db-credentials.yaml -f k8s/app-config.yaml
kubectl apply -f k8s/postgres.yaml
kubectl wait --for=condition=ready pod/postgres-0 -n search --timeout=180s
kubectl apply -f k8s/migration.yaml
kubectl wait --for=condition=complete job/db-migrate -n search --timeout=180s
kubectl apply -f /tmp/app.eks.yaml
kubectl apply -f k8s/ingress.yaml
```

### 8.7 Get the public URL and test

```bash
kubectl get ingress -n search        # wait ~2-3 min for ADDRESS (the ALB DNS) to appear
export URL=$(kubectl get ingress search-service -n search \
  -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')

curl -s -X POST http://$URL/documents \
  -d '{"title":"Kubernetes","body":"Container orchestration platform on AWS"}'
curl -s "http://$URL/search?q=orchestration" | jq
```

You're now serving a Go search service from EKS, through an ALB, backed by Postgres on EBS. 🎉

## 10. Tear it down (do this — EKS + ALB + EBS cost money hourly)

**Order matters.** Delete the Ingress *first* so the controller removes the ALB before the cluster
goes away — otherwise you can leak an orphaned load balancer that keeps billing.

```bash
kubectl delete -f k8s/ingress.yaml               # 1. removes the ALB
kubectl delete namespace search                  # 2. removes app, db, and releases the PVC/EBS volume
helm uninstall aws-load-balancer-controller -n kube-system
eksctl delete cluster --name $CLUSTER --region $AWS_REGION   # 3. tears down control plane + nodes + VPC

# 4. clean up leftovers
aws ecr delete-repository --repository-name search-service --region $AWS_REGION --force
# check the EC2 console for any stray EBS volumes / load balancers and delete them
```

## 11. Production hardening (what changes for real)

This runbook optimizes for *learning the full path*. For a system you'd actually operate:

- **Don't run Postgres in the cluster — use Amazon RDS/Aurora.** A single-replica StatefulSet has no
  failover, and backups/patching/HA become your problem. In production you'd delete `postgres.yaml`
  entirely and point `PGHOST` at the RDS endpoint with `PGSSLMODE=require`. Everything else (the app,
  the Service, the Ingress) is unchanged — that's the payoff of composing the DSN from env vars.
- **Secrets:** never commit `db-credentials.yaml`. Use **AWS Secrets Manager** + the **External
  Secrets Operator** (or Sealed Secrets), and enable **EKS envelope encryption** for etcd.
- **Images:** push immutable tags (git SHA) or digests, never `:latest`; add image scanning on ECR.
- **Availability:** add a **PodDisruptionBudget**, spread pods with topology-spread constraints, and
  run nodes across ≥2 AZs (already true with the default eksctl setup).
- **Networking:** add **NetworkPolicies** so only the app can reach Postgres; put TLS on the ALB with
  ACM (`alb.ingress.kubernetes.io/certificate-arn`) and redirect HTTP→HTTPS.
- **Observability:** you already run Prometheus/Grafana — scrape the app, add RED metrics (rate,
  errors, duration) and DB connection-pool gauges; ship structured JSON logs.
- **CI/CD:** GitHub Actions to build+push to ECR on merge, then **Argo CD** (GitOps) or
  `kubectl apply` from the pipeline to roll it out.
